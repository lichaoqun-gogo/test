## 1. 生命周期治理流程（引入 / 升级 / 退出）

**通用前置**：各账号能通过 CAS 登录；审批链按「发起人部门专员 → （升级/退出附加使用部门确认）→ 管理部门专员」解析（数据见 0.2）。

### 用例 A1：引入申请全流程（推荐走通）

| 项 | 内容 |
|---|---|
| 前置 | zhangsan（技术部 operator）登录 |
| 步骤 | ① 个人工作台「我的任务」→ 快捷发起「引入申请」；② 填写软件名称（如 Redis 7.2）、所属部门=技术部、引入理由，提交；③ 用 lisi（技术部专员）登录 →「待我审批」应看到该任务 → 同意；④ 用 zhouba（管理部门专员）登录 →「待我审批」审批 → 同意 |
| 预期 | 状态流转 draft→审批中→已通过；审批历史记录两个节点（lisi→zhouba）及意见/时间；发起人「我发起的」看到最终状态 |
| 验证目标 | 审批链解析正确（部门专员→管理专员）；审批历史完整；发起人/审批人权限隔离 |

### 用例 A2：引入申请驳回分支

| 项 | 内容 |
|---|---|
| 前置 | 有 A1 的草稿或新发起一条 |
| 步骤 | 发起引入申请 → lisi 驳回（填意见，如"资料不齐"）→ 发起人编辑修改后重新提交 |
| 预期 | 驳回后任务状态=已驳回（rejected，**可重提态**）；发起人可见驳回意见；不可再审批；发起人可「编辑+重新提交」（重新走审批流，节点重置）；**任务不删除，平台留存记录与审批历史** |
| 验证目标 | 驳回后状态机为可重提（非终态）；重新提交后状态→审批中、节点重置可重新审批；驳回意见保留 |

### 用例 A3：升级申请全流程

| 项 | 内容 |
|---|---|
| 前置 | zhangsan 登录，选择已有项目（如内网项目 ORD-CENTER，负责人 zhangsan） |
| 步骤 | ① 我的任务→「升级申请」→ 选择项目、新版本、理由，提交；② lisi 部门专员审批；③（若模板含使用部门确认）使用部门专员审批；④ zhouba 管理专员审批 |
| 预期 | 升级任务走完审批；使用部门/管理部门节点按解析出现；历史完整 |
| 验证目标 | 升级场景的附加节点（使用部门确认）是否正确解析 |

### 用例 A4：退出申请全流程

| 项 | 内容 |
|---|---|
| 前置 | 同上，选择要退出的项目 |
| 步骤 | 发起退出申请 → 按审批链逐节点审批（lisi→[使用部门]→zhouba） |
| 预期 | 退出任务完整走通；各节点审批人正确 |
| 验证目标 | 退出场景审批链正确 |

### 用例 A5：草稿与撤回

| 项 | 内容 |
|---|---|
| 前置 | 发起引入申请未提交（或提交后审批前） |
| 步骤 | ① 保存草稿 → 列表可见并可继续编辑；② 提交后未审批时尝试撤回 |
| 预期 | 草稿状态 draft；撤回后状态 withdrawn（后端校验是否允许） |
| 验证目标 | 状态机：draft / withdrawn 分支正确 |

## 2. 缺陷处理（外部缺陷 / 内部缺陷）

### 用例 B1：外部缺陷导入（幂等 + 就高不就低）

| 项 | 内容 |
|---|---|
| 前置 | admin 或专员登录（全局治理→风险管理→缺陷台账 / 我的运维→缺陷管理） |
| 步骤 | ① 导入缺陷 JSON（`defect_id=redis#TEST-001`，研判=ignored）；② 再次导入同 defect_id（研判=pending_review） |
| 预期 | ① 状态=ignored；② 状态**升级为 pending_review**（就高不就低，A忽略/B待上会以B为主）；台账仅 1 条记录；同文件重复导入不产生第二条 |
| 验证目标 | 幂等（defect_id 主键 upsert）；研判结论就高不就低；不降级/不回退 |

### 用例 B2：缺陷研判（分配研判人）

| 项 | 内容 |
|---|---|
| 前置 | 已导入待研判缺陷（pending_analysis），如 redis#TEST-001 |
| 步骤 | ① 台账/我的运维 → 缺陷详情 → 点「分配研判人」选 zhangsan（或「自动分配研判人」取主岗）；② 用 zhangsan 登录「待我研判」查看 |
| 预期 | 研判人写入 flow（dispatch_target=zhangsan，dispatch_type='analyze'）；zhangsan 可见该缺陷待研判；**分配后按钮隐藏** |
| 验证目标 | 研判分配链路；主岗自动匹配（project_owner 第一负责人）；**dispatch_type 语义：import 跟踪人（导入者）不算已分配研判人，待研判缺陷始终显示「分配研判人」按钮；跟踪人/研判人统一存 username** |

### 用例 B3：缺陷研判结论 + 审核上会（裂变规则）

| 项 | 内容 |
|---|---|
| 前置 | 已分配研判人的待研判缺陷（pending_analysis） |
| 步骤 | ① 研判人登录研判 → 结论选「需要上会评审」；② 另造一条待研判缺陷研判选「忽略」；③ 对上会缺陷执行「评审（上会）」→「需要修复」；④ 观察裂变结果 |
| 预期 | 研判「忽略」→ 缺陷状态 ignored、无工单；研判「需上会」→ pending_review；上会「需要修复」→ assigned + 裂变：**基础软件只裂变 1 张运维单**（如 Redis→技术部/zhangsan，不再按使用部门拆单）；开源组件按依赖项目拆单（component_snapshot→project_inner，每项目 1 张，处理人=项目负责人主岗）；上会「无需处置」→ ignored 无工单 |
| 验证目标 | 研判结论口径（需上会/忽略，与外部研判一致；直接分配仅漏洞）；裂变拆单新规则（基础软件单运维单、组件按依赖项目）；自动匹配处理人（project_owner 主岗，不再受「负责人部门==处置部门」限制） |

### 用例 B4：处置工单流转（分配→完成→闭环）

| 项 | 内容 |
|---|---|
| 前置 | B3 已裂变出处置工单（待分配/已分配） |
| 步骤 | ① 专员给工单分配处置人（若未自动匹配）；② 处置人登录「待我处置」→ 填写处置备注 → 完成；③ 全部工单完成后 |
| 预期 | 工单状态 pending_assign→processing→completed；全部完成后缺陷自动闭环（closed）；状态历史记录完整；**处置工单只有「完成」操作，无「忽略」通道（上会已确认需处置的工单不得忽略）** |
| 验证目标 | 工单状态机；缺陷闭环条件（全部工单完成）；历史记录；忽略通道已封 |

### 用例 B5：内部缺陷上报→审核→建处置单

| 项 | 内容 |
|---|---|
| 前置 | 普通用户 zhangsan 登录 |
| 步骤 | ① 缺陷管理→上报风险（标题/描述/等级选填）→ 生成内部缺陷编号 DF-xxx，状态待审核；② admin/管理专员审核通过并指定部门+负责人；③ 观察是否生成处置工单 |
| 预期 | 内部缺陷 DF-xxx 生成；审核通过后按指定部门/负责人建处置工单；台账内部 tab 可见 |
| 验证目标 | 内部缺陷全链路（上报→审核→建单，不走裂变） |
